# Elvion CLI / TUI 与 Phase 1 引擎开发计划

## 一、目标与实施基线

根据本地开发技术文档 `docs/writing-block.md`（需求来源，未随仓库分发），首版交付应是**能够完成真实开发任务的单 Agent Coding Engine，并通过 CLI/TUI 使用**。验收闭环为：

**输入需求 → 分析项目 → 制定计划 → 调用工具 → 跨文件修改 → 执行验证 → 有限修复 → 保存会话 → 输出交付报告。**

当前仓库处于 `main`，工作区干净；已跟踪内容主要是 README 和品牌资产，尚无源码、`package.json`、锁文件、测试或 CI。因此按从零建设规划，不把文档中的目标目录视为已有实现。

已确认的产品决策：

- **平台：** Windows 优先，正式验收 Windows Terminal；`bash` 工具明确依赖 Git Bash。
- **界面：** 原生字符 TUI，完整使用现有品牌资产，还原预览的构图、配色与视觉层级。
- **模型：** 首版覆盖 OpenAI Chat Completions、OpenAI Responses、Anthropic、Qwen、Ollama 和自定义供应商。
- **自定义供应商：** 通过已有协议模板配置地址、模型和认证，不加载任意脚本插件。
- **技术：** pnpm Workspaces、TypeScript、Zod、Vitest、SQLite、React + Ink。
- **权限：** 提供每次询问、自动编辑、完全访问三种模式；新会话默认自动编辑，恢复会话沿用保存的模式。

调整原文排期：**将 CLI/TUI 前置，从早期里程碑持续接入真实引擎能力**；完整 Phase 1 仍是最终目标。

## 二、架构、协议与权限

### 工程与模块边界

采用精简模块化 Monorepo：

- `apps/cli`：命令入口、依赖组装、TUI、非交互输出和用户操作适配。
- `packages/*`：分别实现 Kernel、Agent、Model、Context、Prompt、Tool、Session、Task、Execution、Verification、Recovery。
- 配置、进程管理、Git 和本地日志按实际依赖落位，不提前建立 Desktop、Server、Multi-Agent 等空包。

核心职责保持分离：Task 管理任务与依赖，Execution 管理一次执行，Agent 管理推理循环，Verification 决定验收是否通过。CLI 只能调用应用接口和呈现事件，不能直接绕过 Tool Runtime 执行受控操作。

以 Node.js 24.x 为首版运行与 CI 基线，采用 ESM；提交锁文件，不引入 Turborepo。SQLite 通过独立 Repository 访问，数据库操作放入工作线程，避免阻塞 TUI；底层 SQLite API 封装在存储模块内。

### 先冻结的接口

| 契约 | 约定 |
|---|---|
| 模型接口 | `stream(request, { signal }): AsyncIterable<ModelEvent>` |
| 执行接口 | 接收任务、工作区、权限与预算，输出 `AsyncIterable<ExecutionEvent>` |
| 工具接口 | 统一执行参数校验、授权、调用、结果标准化和审计 |
| 审批接口 | 使用唯一请求 ID 关联用户批准或拒绝，拒绝与取消均有明确结果 |
| 验证接口 | 返回检查项、实际命令、退出码、证据、失败原因及总体结论 |

事件统一包含版本、顺序号、时间、关联 ID、类型和结构化载荷。模型流、工具执行、等待批准、验证、恢复和终态均使用明确事件，不依赖解析展示文本推进状态。

### 模型接入

实现四个独立协议适配器：

1. `openai-chat`
2. `openai-responses`
3. `anthropic-messages`
4. `ollama-chat`

OpenAI 双接口分别实现，不能只替换 URL。Qwen 首版使用其 OpenAI 兼容协议配置；自定义供应商选择上述协议之一。

供应商配置包含名称、协议、Base URL、模型、凭据环境变量引用及能力声明。界面提供新增、编辑、连通性检查和模型切换。能力按“供应商端点 + 模型”判断，不静默更换协议或模型。

工具调用参数必须完整接收、解析和校验后才能执行；同时正确关联多次工具调用与结果。Usage 缺失显示未知，不能伪造为零。全部适配器支持本地取消和超时，不把断开连接描述成远端推理必然停止。

### 三种权限模式

| 模式 | 执行行为 |
|---|---|
| 每次询问 | **所有模型工具调用逐次批准**，包括读取、搜索、Git 状态和 Todo |
| 自动编辑 | 授权工作区内读取、搜索和文件编辑直接执行；所有 Shell 命令、Git 写操作及工作区外访问需要批准 |
| 完全访问 | 工作区内外均免审批，使用当前操作系统用户已有权限执行 |

补充规则：

- 只有用户通过 CLI 参数或 TUI 操作能够切换模式，模型、仓库文本和工具输出不能提升权限。
- 新会话默认自动编辑；恢复时沿用保存模式，并始终醒目显示当前权限。
- 完全访问不额外插入审批，但仍保留 Schema 校验、超时、取消、输出限制、审计和脱敏。
- 无交互执行遇到待审批操作时，返回结构化 `approval_required`，不能等待不存在的输入或默认批准。
- Phase 1 是受控执行，**不宣称提供操作系统级沙箱隔离**。

## 三、TUI 完整还原方案

以[预览图](../assets/tui-preview.png)和 `assets/brand` 原始文本作为视觉依据，直接加载狐狸与字标，保留字符、空格及行结构，不重新绘制品牌图形。

### 视觉基线

正式基准环境固定为 Windows Terminal、Cascadia Mono、UTF-8、TrueColor、**160 列 × 42 行**。

必须还原：

- 左侧狐狸与右侧 ELVION 字标。
- `Your Partner in Action.` 标语。
- Runtime、Execution、Tools 三行状态卡。
- 卡内分隔线、底部引导文字和箭头。
- 右上版本号、底部分隔线与输入区域。
- 深色背景和青、蓝、紫渐变，以及绿色正常状态。

版本号读取真实包版本；状态来自真实初始化结果，未配置模型或环境异常时不得显示固定 Ready。

终端窗口外框、圆角和三色窗口按钮由宿主管理。原生字符模式以字符网格、构图、颜色和层级验收，位图发光及噪点不作为逐像素一致要求。

### 自适应布局

| 窗口条件 | 布局 |
|---|---|
| ≥144 列且 ≥36 行 | 69×28 大狐狸与完整字标双栏 |
| ≥116 列且 ≥28 行 | 42×18 小狐狸与完整字标双栏 |
| ≥72 列但不满足双栏条件 | 完整字标、状态卡与输入区 |
| <72 列 | 紧凑文字品牌、必要状态与输入区 |

动态调整窗口时不裁切字符图、不横向溢出。颜色能力不足时降级，支持 `NO_COLOR`。图标采用统一字符符号，不使用 Emoji。

### 组件与交互

组件拆为品牌区、健康状态、消息流、工具调用、审批弹窗、任务进度、Diff、输入框、状态栏和交付报告。

交互约定：

- Enter 发送，Ctrl+J 换行；支持中文输入和多行粘贴。
- 活动执行中 Ctrl+C 取消；空闲时退出，退出时恢复终端状态。
- Esc 关闭普通弹层；审批弹层中视为拒绝，不代表批准。
- 审批展示工具、参数摘要、工作目录和影响范围，只批准当前调用。
- 对话开始后使用紧凑品牌区，保留稳定输入区域与可滚动执行记录。
- `/provider`、`/model`、`/permissions`、`/sessions`、`/resume`、`/new`、`/help` 提供必要操作入口。

首版覆盖首次配置、模型切换、流式响应、工具执行、批准/拒绝、验证、修复、取消、断流、恢复和最终交付状态。

## 四、开发里程碑

每个里程碑通过验收后再推进，不以界面演示或 Mock 结果替代功能完成。

| 阶段 | 主要交付 | 可运行验收 |
|---|---|---|
| **M0：工程与契约** | Workspace、严格 TS、质量脚本、Kernel、事件/错误/取消契约、ADR、CI 基础 | 各包可构建导入；Lint、类型检查、测试、构建实际通过 |
| **M1：品牌 TUI** | 欢迎页、完整品牌资源、布局、输入、状态栏与交互组件 | 基准尺寸及断点快照通过，Windows Terminal 实际截图对照通过 |
| **M2：首个真实闭环** | OpenAI Chat、Agent Loop、Context/Prompt、Tool Registry、审批，以及读取/搜索工具 | 输入真实仓库问题，经过工具读取并流式回答，能拒绝与取消 |
| **M3：完整工具与权限** | 十个 Phase 1 工具、三种权限模式、进程管理、Diff 与变更记录 | 临时真实仓库完成创建、精确编辑、补丁、Shell、Git 和 Todo 操作；负向测试通过 |
| **M4：全部模型接入** | Responses、Anthropic、Qwen、Ollama、自定义供应商配置与能力检查 | 每条链路分别通过文本流、工具调用、多轮结果、错误、取消和 Usage 验收 |
| **M5：会话与任务执行** | SQLite 事件日志/快照、Session、Task DAG、串行调度、重启恢复 | 多步骤任务执行与重启继续通过；未知副作用不重复执行；同工作区写执行互斥 |
| **M6：验证与有限恢复** | 项目扫描、真实脚本发现、验证报告、错误分类、预算与恢复 | 跨文件任务出现失败后能根据证据修复，验证通过才标记完成 |
| **M7：集成与分发** | 非交互 CLI、结构化输出、安装包、PTY E2E、使用文档与发布门禁 | 从打包产物安装后完成端到端任务，资源齐全、退出码正确、相关 CI 全绿 |

### 工具实现范围

完整实现 `bash`、`read_file`、`write_file`、`edit_file`、`grep`、`glob`、`git`、`diff`、`apply_patch`、`todo`。

重点要求：

- 文件工具处理中文路径、UTF-8、CRLF、行范围、大文件、路径穿越、符号链接和 Windows junction。
- 精确编辑校验匹配数量；补丁先校验全部目标及上下文，失败时不能留下未说明的部分修改。
- Git 使用结构化子命令与参数，保护已有改动，不混入无关文件。
- Git Bash 启动诊断支持检测与显式路径配置；超时和取消需要验证真实子进程树退出。
- Todo 仅管理辅助事项，不替代 Task 状态机或验证结论。
- Context 按相关性与预算选择内容，压缩后保留目标、验收条件、关键决策及剩余工作。

### 恢复边界与预算

会话保存到用户本地数据目录，凭据仅保存环境变量引用，不保存明文密钥。事件与快照带版本，恢复时进行校验。

Phase 1 恢复会话、任务和稳定步骤状态。崩溃前结果不明的文件修改、Shell 或 Git 操作标记为“待核实”，先检查客观状态，不自动重放。

初始预算设为每次执行最多 50 个 Agent Turn、100 次工具调用、30 分钟；Shell 默认超时 120 秒，验证命令可显式配置。瞬时错误最多重试 2 次，自动修复最多 2 轮；取消和拒绝授权不能被当作可自动重试错误。

### CLI 与分发接口

提供：

- `elvion`：交互 TUI。
- `elvion run "<需求>"`：非交互任务。
- `elvion run "<需求>" --json`：NDJSON 事件与最终报告。
- `elvion sessions list`、`elvion resume <id>`：会话管理。
- `elvion providers add|list|test`、`elvion doctor`：配置与诊断。
- `--help`、`--version`、`--permissions`：基础控制。

JSON 模式 stdout 仅输出结构化内容，诊断进入 stderr。退出码固定为：成功 `0`、执行失败 `1`、参数或配置错误 `2`、需要批准 `3`、超时 `124`、用户取消 `130`。

构建打包内部 Workspace 模块，第三方依赖使用普通包依赖，随包包含全部品牌资源；安装产物不得依赖开发仓库路径或未发布的内部包。

## 五、验收、交付与阶段边界

最终验收保留四组独立证据：

1. **视觉与交互：** 160×42、144×36、116×28、80×24、窄屏和动态 resize；检查中文、粘贴、滚动、长输出、审批与取消。字符快照之外必须有 Windows Terminal 实际截图对照。
2. **协议与安全：** 各协议覆盖分片 JSON、多工具调用、断流、超时、错误与 Usage 缺失；各权限模式覆盖越权路径、恶意参数、拒绝、工作区外访问和恢复后的授权行为。
3. **真实开发闭环：** 创建文件、跨文件功能修改、修复类型错误、测试失败后修复、重启恢复和最终报告；检查实际 Diff、进程、退出码和持久化结果。
4. **工程与分发：** 新增并实际运行 Lint、Type Check、Unit、Integration、E2E、Build 与安装包冒烟检查；模型真实接入使用用户配置的端点验收，缺少凭据时明确记录未验收，不能以 Mock 代替。

将 AGENTS 的 #复现、#回归、#复发、#验证、#核实、#严谨、#归族、#时间维、#基线、#假绿映射到上述测试记录和验收报告。

正式计划与 ADR 后续落入未被忽略的文档路径；原始技术文档保持需求来源身份，不将其中建议当作已经实现的事实。实现期间仅在 `main` 开发，里程碑验收通过后检查 Diff、使用中文提交信息、Push 到 `origin main` 并核实 CI。

Phase 1 不纳入 Multi-Agent、长期记忆、MCP 扩展、Web Research、真实 OS Sandbox、并行工作区和高级长任务容灾；基础恢复保留。Git Worktree 延后，避免与当前串行执行及项目 main-only 规则冲突。

准备 `.github/workflows/release.yml` 及对应版本的 `release/` 发布说明机制；正式 Release 和发布 Tag 仍须用户明确要求。

本文保留批准时的目标与初始基线，不代表全部功能或验收已经完成。实际实现、命令结果及待验收门槛见 [实施与验收记录](development-status.md)。
