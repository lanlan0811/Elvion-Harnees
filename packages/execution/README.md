# Serial task execution

Automatic planning first performs bounded project discovery through authorized glob/read_file tools. Relevant development instructions and project documents are passed as explicitly untrusted user data to the planner and Agent, never promoted to engine policy. Discovery shares the execution's approval mode, cancellation signal, tool budget and audit events. A supplied trusted plan skips this discovery step.

Interactive approvals use one wrapper for discovery, Agent tools and verification. The request ID, tool-call summary, workspace identity, resolved cwd and scope are durably recorded as approval.requested before calling the UI; legacy requests without cwd use workspace as their fallback. The snapshot is awaiting_approval and unsafe to resume. The matching decision, cancellation, error or mismatched response ID is recorded as approval.decided before any approved operation. Tool Runtime still validates the decision ID. Approval success never makes a checkpoint safe until the associated complete tool batch finishes. Without an interactive handler, no user decision is invented and Tool Runtime returns approval_required.

Before the first model request, execution captures the project's package manager and existing script definitions through the authorized Tool Runtime. Reads use the same approval mode, tool budget and durable audit events as other operations. Verification permits additional checks, but deletion or modification of any original script (including indirect helper scripts) or package-manager declaration stops automatic acceptance and persists `needs_review`. Legitimate script changes therefore require explicit inspection under this conservative first-version policy; the engine does not silently approve a weaker replacement. A project without a manifest may create one, and the first discovered definitions then become the execution's baseline. Existing unreadable, oversized, truncated or invalid manifests fail explicitly.

An execution creates a bounded task plan before enabling tool calls. The planner receives the user's goal and no tools. Its output must be a bare JSON array of one to twenty pending tasks containing unique IDs, dependency IDs, titles and nonempty objective acceptance descriptions. Runtime schemas reject malformed JSON, missing dependencies, cycles, duplicated dependencies, precompleted states and tool calls during planning. A trusted caller can supply `ExecutionOptions.plan`; it passes the same validation.

The TaskGraph schedules one available task at a time. Each task runs through the Agent Runtime and then independently discovered project checks. Only successful project checks allow a task to become completed and unblock a dependent task. A final task's project checks gate the execution's final delivery. Plans must therefore describe independently verifiable increments; splitting a change into intermediate non-building fragments causes that step to fail and enter bounded repair. Verification currently discovers Node package scripts. Acceptance text helps guide the implementation but is not an executable proof of every natural-language requirement.

Planning, Agent turns, all model tools, discovery reads, verification commands, retries and repairs share an execution budget. A model delivery alone never marks a task complete. Approval denial, cancellation, timeout and exhausted budgets stop recovery. Each verification tool's intent and result are persisted before/after execution and are returned in event sequence order. Verification currently returns its queued audit events after its promise resolves; approval callbacks remain available while it is running.

SQLite event/snapshot writes are transactional. An event is returned only after its snapshot and event have been saved together. A failed save ends execution instead of attempting to append with a skipped sequence. Optional versioned execution checkpoints preserve the original goal, model, TaskGraph, current task, verification script baseline, last verification report and cumulative turns, tool calls, retries, repairs and active elapsed time. Resume continues the original graph without replanning; callers cannot replace its goal, permissions, model or budget limits. Completed sessions return their saved report without calling a model or tool. Terminal stopped checkpoints remain stopped rather than automatically restarting failed or cancelled work.

Safe checkpoints exist before a model request, after a complete tool-call batch, after delivery, after a completed verification report and between verified tasks. Each network request, including context compaction, first persists its consumed turn and an unsafe `model.requested` intent. A crash during an uncompleted request, tool intent or partial tool-call batch requires review; the engine never guesses whether a pending mutation ran. A durable verification result is consumed without rerunning its shell command. Task starts and terminal transitions persist the actual TaskGraph status, including failed and cancelled nodes. Legacy version-1 snapshots remain readable; completed legacy reports can be restored, while legacy active executions without a validated checkpoint require review.

Saved and requested workspace paths are both resolved through realpath before resume comparison, so Windows short names and junction aliases of the same directory are accepted. The persisted workspace identity remains unchanged; different directories, providers and active models are still rejected. Local workspace lock files prevent concurrent executions. A real process crash can leave a lock even at a safe checkpoint: an operator must inspect the recorded process and actual workspace before removing that stale lock and retrying resume. Automatic stale-lock removal is intentionally unavailable. Normal iterator closure releases the lock and permits a later process to continue. This is controlled execution using the current OS account, not an operating-system sandbox.

Known environment credential values and recognizable bearer/API token forms are redacted before presentation, model history reconstruction and persistence. Text deltas retain a bounded tail so credentials fragmented across model chunks are not exposed as separate prefixes. This is defense in depth, not a guarantee that arbitrary user secrets can be identified. Permission mode comes only from the trusted execution options or validated session state. Historical system messages are replaced with the engine's own prompt when a new Agent loop starts.
